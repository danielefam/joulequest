# Energy Lookup-Table Measurement Audit

**Audit date:** 2026-07-28
**Boards:** Jetson Nano and Raspberry Pi 5
**Acquisition:** INA226EVM at 100 Hz
**Campaign target:** 100 measured cycles per experiment

## 1. Scope

This audit follows the complete measurement path:

1. `automated_measurement.py` starts acquisition on the controller host and
   executes `run_manager.py` on the remote board over SSH.
2. `run_manager.py` calibrates the inference count and records 100 burst start
   and end events.
3. `ina226_serial_logger.py` samples board power into a CSV file.
4. `processing_report/data_processing_new.py` assigns CSV samples to the burst
   windows and computes energy per inference.
5. `processing_report/process_and_visualize.py` averages the 100 cycle results
   into the board summary.

The audit inspected all available CSV/JSON pairs and the generated summaries in
`Plot/jetson_nano_base` and `Plot/raspberrypi5`.

## 2. Current energy definition

The processor currently reports idle-subtracted, or incremental, energy:

$$
E_{incremental/inference}=
\frac{(\overline{P}_{active}-\widetilde{P}_{idle})T_{active}}
{N_{inferences}}
$$

This is not the same as the total board energy used during an inference:

$$
E_{total/inference}=
\frac{\int_{burst}P(t)\,dt}{N_{inferences}}
$$

The final lookup table should identify which definition it uses. Preferably it
should contain both values. Negative incremental energy must be treated as a
quality failure, not clamped to zero.

## 3. Critical problem: cross-host clock misalignment

Burst timestamps and INA226 timestamps are generated by different computers:

- `run_manager.py` records `BURST_START` and `BURST_END` using the remote
  board's UTC clock;
- `ina226_serial_logger.py` records CSV timestamps using the controller host's
  UTC clock;
- `data_processing_new.py` compares these timestamps directly;
- the SSH control path does not estimate, verify, or store the difference
  between the two clocks.

The manifest therefore assumes that the board and controller UTC clocks are
synchronized more accurately than one 10 ms sampling interval. The artifacts
show that this assumption is false.

### 3.1 Measured evidence

For the first small Linear experiment on each board, the interval between local
acquisition readiness and the remote first burst, after subtracting the 5 s
leading idle period, was:

| Board          | Experiment       | Apparent remote-host offset plus first preparation |
| -------------- | ---------------- | -------------------------------------------------: |
| Jetson Nano    | `Linear_64_64` |                                        15.476436 s |
| Raspberry Pi 5 | `Linear_64_64` |                                        16.871273 s |

Preparation for these small layers is negligible relative to a 15-17 s
difference. A local power-contrast search also selected approximately the same
correction.

Applying this correction as a diagnostic changed the results as follows:

| Board                           |      Current result | Clock-corrected diagnostic result |
| ------------------------------- | ------------------: | --------------------------------: |
| Jetson Nano,`Linear_64_64`    | -3.700 uJ/inference |               93.030 uJ/inference |
| Raspberry Pi 5,`Linear_64_64` | 18.318 uJ/inference |              110.859 uJ/inference |

For the Jetson example, 91 of 100 cycles were negative before correction and
none were negative afterward. For the Raspberry Pi example, four cycles were
negative before correction and none were negative afterward.

The first-burst approximation is not a general recovery method because larger
layers can spend significant time preparing parameters and inputs. Existing
large-layer artifacts cannot be corrected defensibly without an independent
clock-offset measurement.

### 3.2 Required correction

Do not use independent UTC timestamps as the only synchronization mechanism.
Before acquisition, perform several controller-board time exchanges and retain
the sample with the lowest round-trip time. Record:

- controller monotonic send and receive times;
- board monotonic and UTC response times;
- estimated board-to-controller offset;
- round-trip time and resulting alignment uncertainty.

Translate board burst events into the controller's monotonic time domain, then
map them to the CSV `Elapsed Time (s)` axis. Reject a campaign when the estimated
alignment uncertainty is too large for the 10 ms sample interval. Chrony/NTP can
support the setup, but the campaign must still verify and record the offset.

## 4. Invalid campaigns enter the summary

The artifact loader checks only `status == "COMPLETE"`. It carries
`quality_status` into the summary but does not reject `REVIEW`. The visualizer
also records `expected_cycles` and `detected_regions` without requiring them to
match.

Observed summary problems:

| Board          | Summary rows | `REVIEW` rows | Negative energy rows | Region-count mismatches |
| -------------- | -----------: | --------------: | -------------------: | ----------------------: |
| Jetson Nano    |          264 |             164 |                   89 |                      36 |
| Raspberry Pi 5 |          123 |              94 |                   57 |                       0 |

The 36 Jetson mismatches contain only 97-99 detected regions instead of 100.
They still contribute an energy mean. Negative values also occur in rows marked
`OK`, because `quality_status` is decided before post-processing and contains no
energy-sign or region-count checks.

This behavior conflicts with `adaptive_burst_measurement.md`, which states that
`REVIEW` campaigns must not enter the final lookup table without investigation.

### 4.1 Required lookup-table gates

A campaign must be excluded unless all of the following are true:

1. Manifest and acquisition status are `COMPLETE`.
2. Manifest cycle labels are exactly 1 through 100.
3. `len(measurement.cycles) == plan.number_of_cycles == 100`.
4. `detected_regions == expected_cycles == 100`.
5. Every cycle has the expected executed inference count.
6. No cycle has unresolved quality flags.
7. Every active region contains the required number of fresh INA226 samples.
8. Timestamp parsing succeeds for every CSV row.
9. Clock-offset uncertainty is below the configured tolerance.
10. Total energy is positive; significantly negative incremental energy causes
    rejection.

Processing should produce separate accepted and rejected tables, with an
explicit rejection reason for every excluded campaign.

## 5. Burst sizing has no safety margin

The inspected campaigns use:

```text
target_burst_seconds = 0
min_active_samples = 100
sampling_rate_hz = 100
```

The calibration therefore sizes most bursts directly on the one-second,
100-sample boundary. Runtime variation then moves many cycles below the minimum:

| Board          | Under-resolved cycles | Fraction |
| -------------- | --------------------: | -------: |
| Jetson Nano    |        2,995 / 26,400 |    11.3% |
| Raspberry Pi 5 |        3,233 / 12,300 |    26.3% |

The sizing calculation needs headroom. Suitable options are:

- target 2-5 s per active burst at 100 Hz;
- require 200-500 samples per cycle;
- multiply the calibrated inference count by a safety factor such as 1.2-2.0;
- run a short validation burst after calibration and increase the count when it
  misses the target.

One hundred cycles can still be retained. Longer bursts improve the energy
estimate within each cycle, while the cycle count characterizes repeatability.

## 6. Global idle baseline can bias incremental energy

The current processor computes one global median from every sample classified
as idle and subtracts it from all 100 active regions. Board idle power can drift
with temperature, DVFS, background services, and power-management state over a
long campaign.

In the clock-corrected Raspberry Pi `Linear_64_64` diagnostic:

- corrected global idle was 0.945266 W;
- per-cycle nearby idle medians ranged from 0.876172 W to 1.067345 W;
- local instead of global baseline changed the mean by approximately 2.4%.

Use a local idle estimate from the uncontaminated idle interval adjacent to each
burst. Exclude input generation, parameter randomization, health checks, and
transition samples. Retain the global baseline and local-baseline range as drift
diagnostics.

## 7. Integration should use measured elapsed time

The current region duration is `active_sample_count / sampling_rate_hz`. The CSV
already contains monotonic `Elapsed Time (s)` values, so energy should be
integrated using those measured deltas:

$$
E \approx \sum_i (P_i-P_{idle,i})\Delta t_i
$$

This is not a major error in the current artifacts: actual-delta integration
changed the two corrected representative means by only about 0.006%. It is still
the correct implementation and makes deadline misses auditable.

## 8. Sensor-rate observations

The 100 Hz request is supported by the recorded INA226 configuration:

- every inspected CSV uses configuration `0x4127`;
- its shunt-plus-bus conversion cycle is 2.2 ms;
- the corresponding fresh-conversion rate is approximately 454.5 Hz;
- achieved logger rates remain approximately 100 Hz;
- the largest observed deadline-miss counts were 9 on Jetson and 12 on
  Raspberry Pi over tens of thousands of samples;
- timestamp parsing produced no failures in the inspected representative files.

Therefore, sampling throughput is not the dominant source of the current error.
The 100 Hz rate is reasonable after clock alignment is fixed and verified.

With `max_expected_current_a=5`, the INA226 power-register resolution is about
3.815 mW. This is usable for the larger offsets but coarse for effects of only a
few milliwatts. The current range should be set as low as safely possible without
register saturation, and saturation checks should be part of campaign quality
control.

## 9. Workload interpretation

The active PyTorch path defaults to `from_state_dict=False`. It constructs a
Linear or Conv2d layer from the filename and randomizes its parameters before
each burst. The table therefore represents randomly initialized operators by
shape, not the trained weights stored at each model path.

This is valid if the intended key is board, backend, operator type, dimensions,
dtype, and batch size. It is not sufficient if the intended table describes a
specific trained model, sparse weights, quantized execution, or data-dependent
control flow.

The manifest should also record the operating conditions that define a lookup
entry:

- exact board and power rail measured;
- backend and framework versions;
- dtype, batch size, and thread count;
- Jetson power mode and clock policy;
- CPU governor and frequency policy;
- start/end board temperature;
- ambient/setup identifier;
- shunt resistance, current range, INA226 configuration, and calibration.

## 10. Statistical interpretation of 100 cycles

One hundred cycles from one continuous campaign characterize within-run
variation. They do not capture variation across reboots, thermal starting
conditions, software states, or different campaign times.

For a final lookup table:

1. Retain 100 valid cycles per campaign.
2. Repeat every configuration in multiple independent campaigns.
3. Randomize model order to reduce temperature and time-of-day confounding.
4. Store mean, median, standard deviation, confidence interval, valid-cycle
   count, and rejection count.
5. Compare independent campaigns before merging them into one table value.

## 11. Artifact status from this audit

- All completed Raspberry Pi manifests contain exactly 100 cycles.
- All completed Jetson manifests contain exactly 100 cycles.
- Requested and executed inference counts match in completed cycles.
- Jetson also contains 33 failed manifests; failed artifacts are not included in
  the current summary.
- The repository's 57 unit tests pass.
- Existing tests do not cover cross-host clock offset, negative-energy
  rejection, post-processing quality gates, or mandatory 100-region matching.

## 12. Recommended implementation order

1. Stop using the current summaries as final lookup tables.
2. Implement and record remote-to-controller monotonic clock synchronization.
3. Add strict post-processing acceptance and rejection gates.
4. Add burst-duration headroom at 100 Hz.
5. Integrate using CSV elapsed-time deltas.
6. Report total and local-baseline-corrected incremental energy separately.
7. Record board operating state and sensor configuration.
8. Add focused tests for synchronization, 100-region validation, negative
   energy, `REVIEW` exclusion, and irregular sample timing.
9. Rerun the campaigns and perform independent repeats before publishing the
   lookup table.
